# Rungent integration guide for coding agents

This is the canonical short context for an AI coding agent integrating Rungent.

1. Define one `Agent` for one product assistant. Do not introduce skills or routing unless the
   product genuinely has multiple independent capability domains.
2. Define business operations with `@tool`. The first parameter is `ToolContext`; all other typed
   parameters become the model-facing JSON Schema.
3. Declare `effect` and `approval` explicitly. Never infer safety from a function name.
   Every `approval="always"` tool must provide a concrete `confirmation` string or callable that
   identifies the affected object and impact; never ask users to approve only a generic tool title.
   Equivalent successful non-read calls are deduplicated per Run; prefer a batch/count argument and
   use `deduplicate=False` only when identical repeated writes are intentional.
4. Put durable service factories in `ToolContext.deps`, stable resource identifiers in
   `ToolContext.resource`, and read the accepted input from `ToolContext.current_input`. After
   `request_input` resumes, `ToolContext.interaction_response`
   contains the runtime-validated interaction ID, kind, prompt, and value for that response only;
   declare `requires_interaction_response=True` when a host operation must reject model-invented
   answers. Rungent exposes that tool only after a real answer and consumes the answer once.
5. Use `Runtime` for session/run lifecycle. Do not write a second tool loop. The default bounded
   loop allows 16 model steps. Retryable timeouts, transport failures, HTTP 408/429, and server
   errors retry inside the same step up to three times; empty completions consume a new bounded
   step and never become empty user messages.
6. Use the FastAPI router from `rungent.fastapi` when exposing the assistant over HTTP. Use
   `rungent.mcp.create_mcp_asgi` to expose the same tools to an external MCP client without starting
   a Run. Host applications own OAuth; `Agent.export_skill()` only drafts a Skill file. Run
   creation returns `202` with a Run ID; subscribe separately so disconnecting the event stream
   never cancels execution. Pass `Idempotency-Key` when a client may retry creation.
   `GET /sessions` lists the caller's sessions newest first. Hosts set `Session.title` with
   `Runtime.set_session_title` or `PATCH /sessions/{id}` after the first Run.
7. Consume the SSE stream with `@rungent/sdk`. Do not parse provider-specific model chunks in the
   frontend.
8. Use `request_input` for missing information. Group two to eight independent, already-known
   questions in one `form`; ask sequentially only when a later question depends on an earlier
   answer. A `choice` may declare `multiple` and `allow_custom`; choice responses use
   `{selected: string[], custom?: string}`. Form responses use `{answers: {question_id: value}}`.
   All responses are validated by the runtime. Destructive approvals are generated by Rungent,
   not by prompting the model to ask “confirm?”.
9. Rungent exposes public work activity, not raw chain of thought. The model may call the built-in
   `report_progress` alongside business tool calls during multi-step work, never as a dedicated
   model step; model steps, tools, interactions, and progress are
   persisted as ordered public events and projected by the SDK as `state.activities`.
   Terminal Run events settle every unfinished activity; transport failures should call
   `failRungentState` so a stale spinner can never survive an interrupted request.
   Long-running host tools may call `await ctx.report_progress(message, public=...)`; Rungent
   persists and streams each update while the tool is still executing. Updates from one tool call
   share a stable activity ID, remain `running` while work continues, and replace one projected SDK
   row; the ordered event log still retains every update for replay and audit.
10. Add deterministic baseline cases before enabling a real model baseline. Export a
   `BaselineSuite` and run `rungent baseline module:suite` in the host project.
   Tool and interaction expectations are exact by default; use their `contains` match modes only
   for live-model cases where safe retries or optional branches are acceptable, and always assert
   final state.
11. Read `docs/ai-reference.mdx` for the full public API and `examples/roasea/` for the reference
    application pattern.
12. Model user-sized business intents as atomic host tools. Stage large imports in the host
   application, return their diff through `ToolResult.public`, clarify with `request_input`, and
   commit the reviewed draft with one revision-checked atomic tool and one approval. Likewise, a
   reversible “change every leg” request should be one host batch tool, not many single-item calls;
   increasing the model-step limit cannot repair an undersized business interface.
13. Model-facing tool results carry `tool_status: success|error`. Only explicit success envelopes
    participate in deduplication; exceptions, timeouts, and `ToolResult(data={"ok": false})` remain
    retryable. Call `client.cancel(runId)` before aborting the stream's `AbortSignal`; the cancel
    endpoint terminates the active drive and persists `run.cancelled`. Treat `cancelled` as a
    distinct terminal state.
14. Add trusted provider-specific top-level request fields through
    `OpenAICompatibleModel(extra_body=...)`. Core request fields cannot be overridden. For
    latency-sensitive Qwen runs, for example, use `{"enable_thinking":false}`.
15. Malformed or truncated tool-argument JSON is retried inside the same model step. Rungent resets
    partial text and asks the provider for compact valid JSON before any tool can execute.
16. A host tool may return `ToolResult.interaction=InteractionRequest(...)` with a frozen
    continuation tool. Rungent persists and displays that question immediately, then executes the
    typed `requires_interaction_response` continuation directly after a validated answer without
    spending another model step. Use `allow_skip` only when skipping is safe for the workflow.
17. Latency-sensitive agents should declare `run_activity`, returning public `RunActivity`
    messages authored by the host application. Rungent emits the first activity immediately and,
    while a provider stream is silent, updates the same persisted activity after three seconds and
    every five seconds thereafter. Progress activities remain `running` until real model work
    advances or the Run terminates; never use this channel for hidden reasoning. Products that
    require finite deadlines may set per-attempt `model_step_timeout_seconds` and overall
    `model_step_total_timeout_seconds`; retries receive a fresh per-attempt budget.
18. Bounded-loop exhaustion keeps the numeric model-step limit in operator state and emits a safe
   `run.failed` envelope with `code=model_step_limit_exceeded` and `retryable=true`. Product UIs
    should localize recovery guidance from the code instead of displaying internals.
19. `request_input` rejects numbered alternatives embedded in a `text` prompt; use `choice` so the
    client can render typed options and a custom-answer row. Tool activities expose stable failure
    codes, allowing product UIs to suppress or localize technical validation noise.
19. Assistant message content is an opaque string to Rungent and `@rungent/sdk`. The host Agent owns
   its writing-format instructions, and the product frontend owns Markdown parsing, sanitization,
   link policy, and styling. Rungent intentionally does not declare a content format or ship a
    renderer.
20. A host tool may return `ToolResult.deferred=DeferredRequest(...)` for durable work that depends
    on a browser or worker observation. Rungent persists the task binding, moves the Run to
    `waiting_external`, and spends no model steps while waiting. Host code reports public progress
    and calls `Runtime.resume_deferred` exactly once with an authoritative terminal result. The
    runtime atomically claims and leases that resumption before returning to the model, so recovery
    workers cannot mistake active continuation work for an interrupted Run. Connect
    `external_task_canceller` when cancelling the Run must cancel host-owned work. Keep domain job
    state in the application, not Rungent.
21. Applications with an obvious deterministic entry path may declare `Agent.run_initializer`.
    It returns at most one registered typed `ToolCall` before the first model step; Rungent applies
    the same validation, interaction, deferred, and event rules as it does to model calls.
